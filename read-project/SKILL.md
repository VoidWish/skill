# Codebase Orientation

在修改代码、排查 bug 或实现功能之前，先把代码库解释成一张有证据的地图。这个 skill 只负责理解和说明，不负责修复问题。

## 只读边界

- 先确认工作目录和仓库范围，使用 `rg --files`、目录列表和现有文档建立文件清单。
- 阅读 README、其他 Markdown、构建/依赖文件、入口文件、相关源码和测试；根据项目规模调整范围，并说明没有读到的部分。
- 默认不修改、删除、重命名或格式化任何文件，不安装依赖，不生成测试文件，不重构代码。
- 不要根据文件名、常见业务模式或框架习惯补全需求。无法从仓库证实的内容写入“无法确定”，并说明需要哪份文档或测试才能确认。
- 可以执行不会写入工作区的查看命令。不要为了说明项目而启动服务、执行可能生成缓存或数据库变更的命令；若必须运行测试，先说明可能的副作用并保持只读。

## 调查顺序

1. **确定边界**：记录仓库根目录、主要语言/框架、构建入口、依赖清单和测试命令（仅在文件中明确出现时记录）。
2. **建立目录地图**：找到应用入口、核心模块、配置、适配器/接口层、数据层和测试；不要把每个辅助文件都写成重点。
3. **追踪一条完整路径**：从启动函数、CLI/API/任务入口开始，沿调用关系追到关键处理、持久化/外部调用和最终输出。用函数、类或模块名标记每一跳。
4. **对照测试和文档**：说明哪些行为由 README、测试或注释直接证明，哪些只是代码推断；记录测试覆盖到和没有覆盖到的边界。
5. **先报告后行动**：输出理解报告后停止。只有用户明确要求下一步排查或修改时，才进入其他工作流。

## 输出格式

用中文大白话回答，保留用户可继续追问的技术名词。必须包含以下六节：

1. **项目解决什么问题**：用一两句话说明目标，并列出证据文件和函数/类/模块。
2. **程序从哪里开始运行**：指出实际入口（例如 `main()`、路由注册、CLI 命令、任务调度器），说明启动到第一步业务处理的调用链。
3. **每个模块负责什么**：只列核心模块。每行包含 `路径`、`函数/类/模块符号`、白话职责和证据。
4. **一次完整请求的数据流**：按顺序写输入如何进入、经过哪些函数、如何改变或校验、如何调用外部系统、怎样形成输出；没有 HTTP 请求时，用一次命令、任务或测试执行代替。
5. **输入、输出和约束**：分别列字段/参数、返回值/文件/副作用、配置、版本、错误处理和测试中能确认的边界。
6. **当前无法确定的地方**：只写无法由现有仓库确认的事项，给出缺少的证据；不要用猜测填空。

每个实质性结论都要带证据，至少写出相对路径和函数名/类名/模块名；能确定行号时再附行号。对模块级结论可用文件级模块名，但不能只给目录名。建议用下面的证据表：

| 结论 | 证据（路径 + 符号） | 证据类型 |
| --- | --- | --- |
| ... | `src/...py: function_name` | README / 源码 / 测试 / 配置 |

将内容明确分成“仓库直接说明”“源码可见行为”“尚未证实的推断”。不要声称运行过没有实际运行的命令，也不要声称测试通过而没有输出证据。

## 首轮提示词

当用户要把这套流程交给另一个 coding agent 时，可直接使用：

```text
请先阅读 README、源码、测试和目录结构，暂时不要修改任何文件。

请用大白话说明：
1. 这个项目解决什么问题；
2. 程序从哪里开始运行；
3. 每个模块负责什么；
4. 一次完整请求的数据流转过程；
5. 输入、输出和约束；
6. 当前代码中哪些地方你无法确定。

每个结论都请给出对应的文件名和函数名，不要根据常见业务自行补充规则。
请区分文档直接说明、源码可见行为和无法确认的推断；完成报告后停止，不要修改文件。
```

## 常见失误

- **只总结 README**：继续读入口、实现和测试，确认文档是否过时。
- **把文件名当职责**：沿调用关系和测试断言核实实际行为。
- **直接找“问题”并改代码**：本 skill 先建立事实；调试要等用户明确提出，并切换到系统化调试流程。
- **只报模块名称不报符号**：补充函数、类、路由处理器、任务函数或模块级变量。
- **把“能运行”当“需求完成”**：列出未覆盖的边界和没有证据的行为。
- **为了理解而产生副作用**：不安装包、不启动服务、不写缓存或临时文件。
